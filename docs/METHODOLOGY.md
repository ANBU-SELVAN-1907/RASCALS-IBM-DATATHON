# Evaluation protocol

## Data and target

The simulator emits one aggregate event per service per second for four services. It represents request count, observed failure count, p95 latency, database pool occupancy, queue, retries, CPU and memory. These are synthetic aggregate observations, not captured real transactions or independently deployed hospital services.

The target is a **new service-objective breach within the next 60 seconds**. A breach requires p95 latency above 1,000 ms or failures/requests above 10% for three consecutive windows. Already-breached windows and windows without a full future horizon are excluded from forecast fitting and point-level PR-AUC/Brier evaluation. Incident-level evaluation processes full runs, including missed, late, and abrupt outcomes.

Each feature uses only current and prior observations from its own service. Fifteen-observation means and slopes are maintained in bounded deques. Features do not contain fault type, scenario ID, seed, fault onset, future values, the synthetic intervention label or the target. Service identity is encoded as declared context.

## Whole-run separation

| Split | Runs | Seed range prefix | Purpose |
|---|---:|---|---|
| Training | 60 | 1000-series | Fit forecast candidates, novelty and statistical reference |
| Calibration | 18 | 10000-series | Fit sigmoid probability calibration and novelty reference distribution |
| Validation | 24 | 20000-series | Joint forecast-model/alert-policy selection and robust baseline threshold |
| Final test | 60 | 70000-series | Frozen v3 evaluation |
| Unseen abrupt stress | 6 | 80000-series | Sudden failure without a gradual precursor |

Training and normal references cover healthy, healthy surge, healthy workload shift, pool exhaustion, retry storm and memory pressure as applicable. The v1 30000-series and v2 50000-series evaluations were inspected. v3 corrected the scoring horizon and reselected the policy using validation before evaluating fresh 70000-series seeds. Those development reports remain in artifacts; they are excluded from the current final claims.

The final test is still generated by the same simulator family, so independent seeds do not establish cross-domain generalization. The independent sampling unit is a run; dependent services in one run are correlated.

## Models and selection

Forecast candidates: scaled logistic regression, seven-leaf histogram gradient boosting, and fifteen-leaf histogram gradient boosting. Sigmoid calibration fits each candidate's clipped probability logits on separate calibration runs. Thresholds 0.20–0.97, three novelty cutoffs, and forecast/hybrid/threshold-guarded policies are compared on validation.

Validation objective: `0.65 * early_warning_recall + 0.35 * incident_precision - 2 * max(0, healthy_false_alarms_per_hour - 0.5)`. This is an explicit engineering policy, not a scoring rubric supplied by IBM. The selected v3 model is the seven-leaf boosted tree; selected alert policy is guarded_forecast at 0.97 (learned forecast OR static thresholds). Isolation Forest remains an independently displayed novelty signal and evaluated comparator, not an alert trigger in the final policy.

Static baseline uses documented thresholds: p95 above 800 ms, pool above 90%, error fraction above 8%, or CPU above 90%. These are fixed engineering thresholds rather than an exhaustively optimized baseline. The robust statistical detector uses positive standardized departures from normal medians/MADs; its cutoff is selected on validation. Do not claim comparison with every possible threshold strategy.

## Alert episodes and matching

All detectors use three flags out of the last five windows after warmup. Each service's latch clears when all five flags are false, with a 30-second minimum cooldown between alerts. Breach windows separated by at most 15 seconds are one incident.

An alert can match one incident from 60 seconds before its first sustained breach through 15 seconds after its end. Each incident can match one alert. Additional alerts are unmatched and count against precision. The matching allowance now agrees with the 60-second forecast target. Earlier v2 results used a 90-second allowance and are retained only as development history. No point adjustment retroactively marks all incident windows correct.

Healthy-run false alarms count alert episodes during the three healthy scenario families, divided by their full service-hours, including warmup. Across all runs, unmatched alerts also include faults that do not reach a breach, very early alerts outside the matching window, and repeat alerts. Consequently zero healthy-run false alarms can coexist with 59.3% overall precision.

## Response preview

No-action and action branches share the same demand/noise arrays, seed and state history until intervention. The fixed rule chooses a runbook from observable retries, memory and pool values. Only allowlisted simulator actions are possible. Report improvements together with deferred optional work. The simulator encodes the effect of these actions; this is not causal evidence from production or proof that a real intervention will work.

## Timing boundary

The saved benchmark measures direct engine calls over paced 8-second trials, with four events per batch. It includes feature extraction, both predictive score paths, persistence logic, incident handling, and SQLite commits. It bypasses HTTP and ingestion queue waiting, and excludes browser rendering. Generator time and 15-window warmup/persistence affect warning timing but are not included in the per-batch processing latency. No claim of sustained peak capacity follows from these short trials.


Two runtime trials are retained: `runtime-benchmark-initial.json` and `runtime-benchmark.json`. At 100 events/s their p95 batch times were 9.03 and 53.60 ms. The repeat overlapped container preparation and local generation activity; resource contention was not experimentally controlled. Both accepted 800 events in eight seconds. Those historical runs predate the engineering audit. Current native correctness counts and HTTP timings are in correctness-report.json and http-benchmark.json; see RESULTS.md. Neither run establishes steady-state production capacity.


## Uncertainty and HTTP integration
The v3 report resamples whole runs 500 times with a fixed bootstrap seed, retaining dependent services together. Percentile intervals describe the synthetic family and do not establish production efficacy. The native HTTP benchmark uses a separate app, loopback port and temporary SQLite state, with synthetic fixtures and generation off. Queue-ack, engine-batch processing and final confirmation have separate timing boundaries. No browser or WAN latency is inferred.
